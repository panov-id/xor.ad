## 🔴 1. Audit-журнал утекает между арендаторами

`tenant_admin` имеет право `logs.audit.read`, а роут отдаёт весь платформенный
журнал без фильтра — комментарий обещает фильтрацию, кода нет:

```ts
// routes/admin.ts — было
const page = await readLogPage<Record<string, unknown>>(
  scopedForBrand(null), // one platform-wide trail, filtered per reader  ← обещание
  auditDir(), window, HISTOGRAM_BUCKETS,
);
```

Арендатор `alpha` читает записи о том, кого `beta` пригласил в панель и когда.
`test/tenancy.test.ts` этот роут не покрывает вовсе.

**Решение.** Фильтр внутри `readLogPage`, а не после него: фильтрация снаружи
оставила бы `total`, `matched` и гистограмму от полной коллекции — то есть
счётчики продолжали бы рассказывать про чужую активность.

```ts
// routes/admin.ts — стало
const page = await readLogPage<Record<string, unknown>>(
  scopedForBrand(null),
  auditDir(),
  window,
  HISTOGRAM_BUCKETS,
  // A tenant reads its own slice of the shared trail; the platform reads all.
  access.user.brand === null
    ? undefined
    : (record) => record.actor_brand === access.user.brand,
);
```

Цена: отфильтрованное чтение обязано читать объекты (принадлежность видна только
внутри записи), поэтому у него отдельный путь с потолком сканирования.

## 🟠 2. Окно между деплоем и `--apply`: дубли приветственных писем

Дедуп ищет ключ внутри арендатора, а старые записи лежат в корне:

```ts
// routes/waitlist.ts
const store = scopedForBrand(brand.key);
const key = `waitlist/${config.envName}/${await sha256hex(email)}.json`;
if (await store.exists(key)) { … }   // tenants/sosed/waitlist/… — пусто до миграции
```

С момента выката до `migrate_tenants --apply` каждый уже записавшийся человек,
отправивший форму повторно, получает второе welcome-письмо и создаёт вторую
запись.

**Решение** — транзиторный фолбэк за тем же флагом, что и бескючевые запросы:

```ts
// Transitional: a lead written before the migration still lives in the root.
const seenBefore = await store.exists(key) ||
  (!config.requireApiKey && await scopedForBrand(null).exists(key));
```

## 🟠 3. Публичный роут пишет объект в хранилище на каждый запрос без ключа

`log("warn", …)` в `tenant.ts` копируется в хранилище (`lib/log.ts` персистит
warn/error). Пока `REQUIRE_API_KEY` выключен, любой бот на `/client-error`
создаёт объект на запрос: расходы на хранилище плюс страница серверных логов,
забитая одинаковыми строками.

**Решение** — логировать переход, а не запрос: одна строка на пару
(бренд, origin) в час, остальное в счётчик.

## 🟡 4. Проверка ключа — поход в хранилище на каждый публичный запрос

`findPublishableKey` читает объект всегда. Неверный ключ = промах чтения на
каждую попытку, то есть перебор оплачивается трафиком к хранилищу. Ключи
неизменяемы, кроме отзыва — просится тот же TTL, что у реестра брендов, включая
отрицательный результат. Плата: отзыв вступает в силу за минуту.

## 🟡 5. Ключ бренда попадает в путь без проверки

```ts
const at = brand ? `tenants/${brand}/` : "";   // scoped_storage.ts
```

Сегодня ключи приходят из env и своих рук. Раздел 0 `api-platform_*` обещает
self-service регистрацию арендатора — в этот день `key: "../.."` станет дырой в
чужие данные. Закрывается проверкой формы ключа на входе в реестр:

```ts
const BRAND_KEY = /^[a-z0-9][a-z0-9-]{1,31}$/;
```

## 🟡 6. `/client-error` спорит с логгером

Роут построен на принципе «никогда не спорить с логгером» (`if (!body) return
json({ ok: true })`), но теперь возвращает 401/403 при плохом ключе. Лендинг со
старым ключом перестаёт присылать ошибки и не может сообщить об этом — канал
сообщений и есть этот роут.

**Решение.** Отвечать `200 { ok: true }`, неатрибутированное складывать в
платформенный `client-errors/unattributed/<env>/`: «у кого сломался ключ» видно
в панели, а не по тишине.

## 🟠 11. `migrate_tenants --delete` удалял, отчитываясь «ничего не записано»

Найдено не чтением, а прогоном на локальном стенде: `--delete` без `--apply`
действительно удаляет оригиналы (это и есть третий проход по замыслу), но
печатает `== summary (plan only, deleting)` и в конце
`nothing was written — re-run with --apply`. То есть ровно тот запуск, который
удалил данные, сообщает, что не тронул ничего.

```ts
// было
console.log(`\n== summary (${apply ? "applied" : "plan only"}${remove ? ", deleting" : ""})`);
if (!apply) console.log("\nnothing was written — re-run with --apply");

// стало
const pass = remove ? (apply ? "applied, deleting" : "deleting") : apply ? "applied" : "plan only";
console.log(`\n== summary (${pass})`);
if (!apply && !remove) console.log("\nnothing was written — re-run with --apply");
if (!apply && remove) {
  console.log("\ncopies were not made in this run; originals with a copy were removed");
}
```

Само удаление безопасно — оригинал уходит только после проверки, что копия
читается, — опасна была формулировка.
