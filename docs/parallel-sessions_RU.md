# Параллельные сессии: несколько агентов на одном репозитории

Как запустить 3–6 сессий Claude Code на xor.ad одновременно, чтобы они делили
работу, обменивались данными и следили друг за другом, не ломая друг другу
дерево, миграции и реестры. Документ — для владельца (что открыть и что
написать) и для самих сессий (правила ролей).

## 1. На чём это держится (замерено 26.09.2026)

- **Сессии видят друг друга.** `ListAgents` в сессии xor.ad показал соседей по
  имени (`xor-ad-a1`, `sso-b7`); `SendMessage({to: "<имя>", message})` пишет
  соседу, ответ приходит уведомлением. Имя своей сессии — первая строка вывода
  `ListAgents` («This session is …»).
- **Общая доска — файлы вне репозитория:**
  `/home/eugene-panov/Projects/panov-id/.parallel/xor.ad/`. Вне дерева git, чтобы
  доска не попадала в `git status` и в коммиты.
- **У каждого исполнителя — своё рабочее дерево** (`EnterWorktree`): своя ветка,
  свой индекс, свои незакоммиченные правки. Два агента в одном дереве портят
  друг другу `git add` и незакоммиченное — это главный способ всё сломать.
- **Тесты с базой изолированы по PID:** `scripts/run-relay-database-tests.sh`
  называет сеть и контейнер `relay-test-net-$$` / `relay-test-db-$$`. **Проверено
  прогоном 26.09.2026:** два набора в разных деревьях шли одновременно
  00:19:10–00:21:51 в своих сетях (наблюдатель — `docker ps` раз в секунду и
  `docker inspect`), итоги 364/0 и 365/0, контейнеров после не осталось.
- **`scripts/check-all.sh` в рабочем дереве `.claude/worktrees/*` даёт ложные
  красные** (11 из 12 на 26.09.2026): отслеживаемые ссылки `sosed.place` и
  `neighbro.place` ведут в `../`, то есть в `.claude/worktrees/`, где витрин нет.
  Полные ворота гоняет координатор в основном дереве после вливания; исполнитель —
  тесты своих `files`.

## 2. Роли

| Роль | Сколько | Что делает | Чего не делает |
|---|---|---|---|
| **Координатор** | 1 | Режет работу на задачи, раздаёт номера миграций, ведёт `tasks.tsv`, вливает ветки исполнителей в `day58` в основном дереве, гоняет полный набор перед вливанием, единственный правит общие реестры | Не пишет код задач сам, пока есть свободные исполнители |
| **Исполнитель** | 2–4 | Берёт одну задачу, работает в своём дереве и своей ветке, коммитит туда, доказывает готовность прогоном | Не трогает основное дерево, `day58`, общие реестры; не пушит |
| **Наблюдатель** | 1 | Перепроверяет каждое «готово» (как агент `verifier`), следит за сердцебиением, ловит пересечения по файлам, будит зависших | Не правит код; только читает, прогоняет и пишет сообщения |

Меньше четырёх сессий — наблюдателя совмещает координатор. Больше четырёх
исполнителей не нужно: вливание у координатора становится узким местом.

## 3. Доска

```
/home/eugene-panov/Projects/panov-id/.parallel/xor.ad/
  tasks.tsv            пишет только координатор
  sessions/<имя>.md    пишет только сессия <имя>: роль, дерево, задача, сердцебиение
  log/<имя>.log        дописывает только сессия <имя>: одна строка на событие
  handoff/<имя>.md     передача, когда сессия уходит (8 часов, рестарт)
```

У каждого файла один писатель, поэтому одновременных правок одного файла нет.

`tasks.tsv` — столбцы через табуляцию:

```
id	status	owner	branch	files	migration	evidence	note
A1	claimed	xor-ad-a1	worktree-par-A1	relay/node/src/lib/identity_sweeper.ts	-	-	остаток observability.lockorder.alerts
A2	free	-	-	scripts/report/*	-	-	перенос сборщика отчёта в репозиторий
```

`status`: `free` → `claimed` → `done` (исполнитель прислал доказательство) →
`verified` (наблюдатель подтвердил) → `merged` (координатор влил). Возврат из
`done` в `claimed` — с причиной в `note`.

`sessions/<имя>.md` — пять строк: роль, путь к дереву, задача, `heartbeat:
<ДД.ММ ЧЧ:ММ>`, что делаю сейчас. Сердцебиение обновляется в начале каждого
хода. Старше 30 минут без фоновой задачи — наблюдатель пишет сессии, старше
60 минут — задача возвращается в `free`.

## 4. Где сессии сталкиваются и кто за что отвечает

| Общее место | Правило |
|---|---|
| Номера миграций `relay/node/db/NNN_*.sql` | Номер выдаёт координатор в столбце `migration`; сейчас последняя — `057`. Без выданного номера миграцию не создавать |
| `docs/test-map_*`, `docs/roadmap_*`, `docs/facts/*.tsv`, `docs/open-work_*`, `docs/chat_*` §13 | Правит только координатор после вливания. Исполнитель присылает нужные строки сообщением |
| `relay/node/deno.json`, `package-lock.json`, `depth/package-lock.json` | Задача, которая их меняет, берётся в одиночку: координатор не раздаёт параллельно вторую такую |
| Живые стенды (dev n1, прогоны против живого узла) | Одна сессия за раз; координатор отмечает в `tasks.tsv` строкой `stand` |
| `scripts/run-depth-tests.sh` (и `check-all.sh --with-tests`, который его зовёт) | Пока метка общая (`depth-test=1`), скрипт при старте сносит контейнеры соседних прогонов — одна сессия за раз, строка `stand-depth` (26.09.2026, нашёл наблюдатель) |
| `git push`, выкат | Только координатор и только по слову владельца (правило 10) |
| Голос `/voice` | Не больше чем в одной сессии, иначе фразы перекрывают друг друга |
| Решения внутри утверждённого | Кворум (правило 31) собирает тот, кто упёрся; решение пишет в `decisions.tsv` координатор |

## 5. Как сессии следят друг за другом

1. Исполнитель закончил → коммит в своей ветке → в `tasks.tsv` через координатора
   `done` → сообщение координатору и наблюдателю: ветка, коммит, команда прогона
   и её итоговая строка («364 passed»).
2. Наблюдатель переходит в дерево исполнителя (только чтение), повторяет прогон,
   ломает охраняемое место и смотрит красный (правило проекта «тест, который не
   падал, ничего не доказывает»), возвращает то же, сломав. Итог —
   `verified` или список находок исполнителю.
3. Координатор вливает `verified` в `day58`, гоняет полный набор в основном
   дереве, правит реестры, отмечает `merged` и рассылает всем: «day58 = <sha>,
   перебазируйтесь».
4. Одновременные прогоны с базой проверены 26.09.2026 (§1); наблюдатель
   продолжает следить за контейнерами `relay-test-db-*`, пока идут прогоны.

Что наблюдатель ловит сверх этого: две задачи, у которых пересекаются `files`;
коммит исполнителя в файл вне его `files`; сессию старше 8 часов (правило 28 —
она пишет `handoff/<имя>.md` и останавливается, задачу забирает новая).

## 5а. Цикл в каждой сессии и кольцо перезапуска

Каждая сессия работает в `/loop` (самотактирующемся, без интервала) с текстом
своей роли:

```
/loop Роль <роль> по /home/eugene-panov/Projects/panov-id/xor.ad/docs/parallel-sessions_RU.md: тик роли (§7), затем кольцо (§5а)
```

Тик заканчивается результатом, а не отчётом. Ждать долгое — фоновой задачей
или пробуждением 10–20 минут, не частым опросом.

**Кольцо.** Порядок записан в `ring.txt` на доске, одна строка на сессию; каждая
сессия на каждом тике проверяет следующую за собой (последняя — первую), а
наблюдатель — всех:

1. `heartbeat` в `sessions/<сосед>.md` моложе 20 минут — всё хорошо.
2. Старше 20 минут и сосед в `ListAgents` есть — сообщение соседу:
   «цикл остановился, запусти заново: `/loop …`» с его строкой из `ring.txt`.
   Строка в `log/<я>.log`.
3. Через следующий тик сердцебиение не сдвинулось — сообщение координатору
   (или, если молчит сам координатор, — наблюдателю) и владельцу в ответе хода.
4. Соседа нет в `ListAgents` — сессия умерла: его задача возвращается в `free`
   (пишет координатор), владельцу — одна строка «открой новую сессию на роль …».

Сообщение соседу — просьба, а не команда: разрешения каждая сессия берёт у
своего пользователя, чужим разрешением не пользуется.

## 6. Что написать владельцу

Открыть сессии в каталоге `xor.ad` (так у всех загружается память проекта).
Координатора — первым.

**Координатор:**

```
Ты координатор параллельной работы. Прочитай docs/parallel-sessions_RU.md и
действуй по роли «Координатор». Заведи доску, если её нет. Задачи на сегодня:
<список или «возьми из session-handoff и open.tsv, реши кворумом»>.
Исполнителей будет <N>. Пуш — только по моему слову.
```

**Исполнитель** (в каждой следующей сессии, по одной):

```
Ты исполнитель. Прочитай docs/parallel-sessions_RU.md, роль «Исполнитель».
Зарегистрируйся на доске, напиши координатору и возьми свободную задачу.
```

**Наблюдатель:**

```
Ты наблюдатель. Прочитай docs/parallel-sessions_RU.md, роль «Наблюдатель».
Зарегистрируйся на доске и следи за всеми, пока я не скажу стоп.
```

Точечно, в любой момент, в любую сессию:

- «Статус по доске» — сессия читает `tasks.tsv` и `sessions/`, отвечает таблицей.
- «Передай <имя>: …» — сессия пересылает через `SendMessage`.
- «Сворачиваемся» — исполнители коммитят в свои ветки и пишут `handoff/`,
  координатор вливает `verified` и докладывает, что осталось.

## 7. Первые шаги по ролям

**Координатор:**
1. `ListAgents` — узнать своё имя и соседей.
2. Создать доску (§3), если её нет; записать `sessions/<имя>.md`.
3. Нарезать задачи так, чтобы их `files` не пересекались; выдать номера миграций.
4. Каждый ход: прочитать входящие сообщения и `tasks.tsv`, влить `verified`,
   ответить исполнителям.

**Исполнитель:**
1. `ListAgents` — своё имя; записать `sessions/<имя>.md`.
2. Написать координатору «готов, имя, свободен»; получить задачу.
3. `EnterWorktree` с именем `par-<id задачи>`: ветку `worktree-par-<id>` он
   заводит сам, но **от `origin/main`, а не от `day58`** (замерено 26.09.2026 по
   reflog всех трёх пробных веток: `Created from origin/main`, 684a103). Сразу
   `git reset --hard day58` — дерево свежее, терять в нём нечего — и сверить
   `git log -1 --oneline` с тем, что координатор назвал текущим `day58`.
4. Работать только в своих `files`; всё, что надо поменять в общем (§4), —
   сообщением координатору.
5. Готово — по §5, п. 1. Потом — следующая задача.

**Наблюдатель:**
1. `ListAgents`; записать `sessions/<имя>.md`.
2. Каждый ход: сердцебиения, пересечения `files`, новые `done`.
3. На каждое `done` — повторный прогон и контрольная поломка в дереве
   исполнителя; итог — сообщением исполнителю и координатору.
4. Долгие ожидания — `/loop` с шагом 10–20 минут, а не частый опрос.

## 8. Чего не делать

- Работать двум сессиям в одном дереве.
- Делать `git checkout`, `reset`, `stash` в основном дереве кому-либо, кроме
  координатора.
- Пересказывать находку другой сессии без пометки «ПРОВЕРЕНО чем / НЕ
  ПРОВЕРЕНО» (правило 24): сообщение соседа — заявка, а не факт.
- Слать соседям тексты сессий во внешние сервисы — всё остаётся на машине.
