# Миграции шага 1: личность и сессия

Спека чата (`chat_RU.md` §8.2) описывает три таблицы шага 1 в трёх разных
разделах, вперемежку с доводами. Здесь они собраны в том виде, в каком уедут в
базу: **что, в каком порядке, чем проверяется**.

Написано 28.08.2026, до первой строки кода — по той же причине, по которой раньше
написана карта тестов: спорить о готовности будет не нужно, список выведен из
спеки, а не из того, что оказалось удобно.

## Как устроен механизм, и что из этого следует

Миграции узла — файлы `relay/node/db/NNN_имя.sql`, применяются **в порядке имён,
по одному разу**, факт применения пишется в `schema_migrations`. Инструмент —
`relay/node/tools/migrate_db.ts`, и он **намеренно тупой**: ни отката, ни
контрольных сумм, ни DSL.

Отсюда два правила для шага 1, и оба не про вкус:

- **Только вперёд.** Ошибку в применённой миграции чинит следующая миграция, а не
  правка файла: файл уже записан по имени и повторно не выполнится.
- **Файл читается как схема.** Раз `db/` и есть описание схемы, комментарий в
  миграции стоит ровно столько же, сколько сама колонка.

Сегодня в `db/` тринадцать файлов, `001`–`010` и `012`–`014`: управляющее состояние, квоты, ключи
брендов и API, секретные ключи узла, реестр уведомлений по ст. 16. Продуктовых
таблиц нет ни одной — шаг 1 открывает первую.

## Порядок

Он не выбран, а вытекает из внешних ключей: сессия ссылается на личность, доля —
на сессию.

```
011_identities.sql     →   015_sessions.sql     →   016_vault_shares.sql
                       →   017_legal_acceptances.sql
   личность                 устройство               доля ключа хранилища
```

**Номера прыгают, и это не опечатка (правка 02.09.2026).** План писался
28.08.2026, когда свободны были 011–014. Пока он лежал, соседняя подсистема
заняла 012, 013 и 014 миграциями по ст. 16 DSA, и план молча указывал на занятые
имена: `migrate_db.ts` намеренно туп, сортирует по имени и коллизию не ловит —
её поймал бы только сам выкат. За личностью остаётся 011, остальное сдвинуто на
015–017. Схема чата — 018.

**Три файла, а не один.** Одна миграция на три таблицы читалась бы как «личность
и всё, что к ней прилипло», а это разные сущности с разной судьбой: сессия
замирает при переносе, доля сгорает от десяти неверных ПИНов, личность живёт.
Разделение стоит один лишний файл и экономит разбирательство через полгода.

## 017 — что человек принял

```sql
CREATE TABLE legal_acceptances (
  id               bigserial PRIMARY KEY,
  identity         uuid NOT NULL REFERENCES identities(id) ON DELETE CASCADE,
  document         text NOT NULL CHECK (document IN ('terms', 'privacy', 'guidelines')),
  revision_date    date NOT NULL,
  revision_sha256  text NOT NULL CHECK (char_length(revision_sha256) = 64),
  accepted_at      timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX legal_acceptances_latest ON legal_acceptances (identity, document, accepted_at DESC);
```

- **Добавлено 29.08.2026 — до этого принятие было записано только словами.**
  И экран регистрации, и спека утверждали, что принятая редакция хранится рядом
  с личностью; хранить было нечего, потому что в документах стояло одно
  «последнее обновление», которое человек пишет руками. Теперь пара — дата и
  `sha256` существа текста; проверка витрины (`deploy/check-legal-revisions.py`)
  не даёт им разойтись.
- **Ссылка каскадная.** Личность стёрлась — её принятия уходят с ней: это данные
  о человеке, а не о документе, и переживать его им незачем.
- **Индекс по (личность, документ, время) убыванием** — единственный частый
  запрос здесь «что у неё принято сейчас», а он берёт первую строку группы.
- **`CHECK` на длину хэша**, потому что единственная правдоподобная ошибка
  записи — положить укороченный или пустой хэш и обнаружить это в споре.

## 011 — личность

```sql
CREATE TABLE identities (
  id               uuid PRIMARY KEY,
  name             text NOT NULL CHECK (char_length(name) BETWEEN 1 AND 24),
  age              integer NOT NULL CHECK (age >= 13),
  identity_public_key text NOT NULL,
  recovery_auth_hash  text,
  recovery_wrapped_key bytea,
  name_state       text NOT NULL DEFAULT 'accepted',  -- accepted | pending | rejected
  created_at       timestamptz NOT NULL DEFAULT now(),
  closed_at        timestamptz
);

CREATE UNIQUE INDEX identities_recovery ON identities (recovery_auth_hash)
  WHERE recovery_auth_hash IS NOT NULL AND closed_at IS NULL;
```

- **Публичная половина ключа — единственное, что узел хранит.** Ни секрета, ни
  его хэша: утечка базы не даёт выдавать себя за людей.
- **Колонки восстановления обнуляемые**, хотя с 26.08.2026 заполняются при
  регистрации всегда. Обнуляемость оставлена сознательно, чтобы не переписывать
  схему ради поля, которое и так заполнено.
- **Частичный уникальный индекс** — потому что по этому хэшу идёт поиск на
  публичной ручке восстановления: два кода на две строки ручка разобрала бы
  молча, взяв первую, а промахи там и есть основной трафик.
- **`name_state`** держит правило «пока имя отклонено, мэтч не открывается».

Закрывает утверждения карты: **1.1–1.6** (личность заводится, имя и возраст
обязательны, до первого поста имя никому не видно).

## 015 — сессия

```sql
CREATE TABLE sessions (
  id              uuid PRIMARY KEY,
  identity        uuid NOT NULL REFERENCES identities(id) ON DELETE CASCADE,
  sign_public_key text NOT NULL,
  wrap_public_key text NOT NULL,
  label           text,
  created_at      timestamptz NOT NULL DEFAULT now(),
  last_seen_at    timestamptz NOT NULL DEFAULT now(),
  frozen_at       timestamptz
);

CREATE UNIQUE INDEX ON sessions (identity) WHERE frozen_at IS NULL;
```

**Частичный уникальный индекс и есть правило одной живой сессии.** Второй живой
базa не примет, и обойти это из кода нельзя — именно поэтому правило живёт здесь,
а не в проверке приложения.

Закрывает: **2.1–2.5** (подпись запроса), **4.1–4.10** (перенос личности:
прежнее устройство замирает, у нового своя пара ключей).

## 016 — доля ключа хранилища

```sql
CREATE TABLE vault_shares (
  session       uuid PRIMARY KEY REFERENCES sessions(id) ON DELETE CASCADE,
  auth_hash     text NOT NULL,
  share_enc     bytea NOT NULL,
  attempts_left smallint NOT NULL DEFAULT 10,
  burned_at     timestamptz,
  last_used_at  timestamptz NOT NULL DEFAULT now()
);
```

- **Доля лежит зашифрованной ключом узла** (`004_secret_keys.sql`), а не как есть.
  Иначе дамп базы плюс один скопированный профиль браузера дают офлайновый
  перебор миллиона ПИНов, и весь замысел рассыпается тем самым способом, который
  спека объявляет недопустимым.
- **Доля принадлежит устройству, а не личности**: иначе уведший личность и
  заведший свой ПИН читал бы чужую старую переписку.
- **Сжигание пишет `share_enc = NULL`**, а не только дату: иначе байты остаются
  лежать.

Закрывает: **3.1–3.6** (ПИН, доля, десять попыток), **5.1–5.8** (восстановление
бумажным кодом).

## Чего в шаге 1 нет — и это порядок, а не забывчивость

`feed_messages`, `likes`, `identity_stats`, `matches`, `match_participants`,
`chats`, `chat_participants`, `chat_starters`, `blocks`, `hidden_messages`,
`chat_key_wraps` — одиннадцать таблиц шагов 2–7. Их DDL уже написан в спеке и
переносится сюда по мере шагов. Начинать с них нельзя по §13: без личности нет
ленты, без ленты нет лайка, без лайка нет мэтча.

## Как проверяется, что миграция сделала обещанное

Не глазами и не «применилось без ошибок»:

1. `deno run ... tools/migrate_db.ts --dry-run` — список того, что будет применено.
2. Применение, затем `SELECT name FROM schema_migrations` — файл записан.
3. **Отрицательные проверки**, они же строки карты: `INSERT` с именем в 25
   символов падает на `CHECK`; вторая живая сессия той же личности падает на
   уникальном индексе; `DELETE` личности уносит её сессии и доли каскадом.
4. Тест, который **видели красным**: сломать `CHECK`, посмотреть на падение,
   восстановить. Зелёная миграция, чьё падение никто не видел, ничего не
   доказывает.
