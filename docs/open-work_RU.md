## B. Тенантность: незавершённая функциональность

- [x] **B1. Страницы API-ключей** — 28.07.2026. `GET/POST /admin/api-keys` и
      `POST /admin/api-keys/:id/revoke`; страница показывает ключ целиком (он
      публичен по устройству), список разрешённых Origin и кнопку отзыва.
      Арендатор видит и выпускает только свои — бренд берётся из сессии, а не
      из тела. Отзыв **штампует** ключ, а не удаляет: исчезнувший ключ унёс бы
      с собой ответ на вопрос «что это было и когда мы перестали ему верить».
      Пустой список Origin отклоняется там, где среда требует ключи.
      Выпуск живёт в `lib/api_key.ts`, и CLI-инструмент теперь зовёт ту же
      функцию — ключ, выпущенный двумя путями, рано или поздно получил бы две
      формы.
- [x] **B2. Страница брендов** — 28.07.2026. `POST /admin/brands` пишет в
      реестр, узел подхватывает сразу, остальные — в пределах TTL кэша: именно
      это делает подключение арендатора записью, а не редеплоем. Бренды из env
      показаны с пометкой `environment` и не редактируются — запись поверх
      затенила бы сид копией, которая от него разъедется.
- [ ] **B3. Self-service регистрация арендатора** — раздел 0 `api-platform_*`.
      B2 закрыт, форма ключа проверяется; осталась сама самостоятельная
      регистрация снаружи панели.
- [ ] **B4. Живая проверка входа арендатора** — магик-линк для `tenant_admin`,
      что он не видит серверные логи и не может выдать роль `admin`. Тестами
      покрыто, на стенде не проверялось.
- [ ] **B5. Квоты и лимиты на ключ** — упирается в E1.
- [ ] **B6. Секретные ключи (server-to-server)** — второй тип ключей из
