# relay — регламент релизов и промоушена

**Принцип: собираем релиз один раз, катим один и тот же образ dev → staging → prod.**
Что протестили — то и в проде, байт-в-байт. Никакой пересборки на каждый env.

## Поток

```
локально ──тест── ветка dev ──CI──▶ :<sha> в ghcr
                                       │  scripts/deploy-relay-dev.sh → dev env
                                       │  смоук + ручная протыкка
                                       ▼
                            merge dev → main
                                       │  тег vX.Y.Z (+ GitHub Release notes)
                                       ▼
                     CI собирает релизный образ :vX.Y.Z (раз) ──▶ ghcr
                                       │
                                       ▼  катим ТОТ ЖЕ :vX.Y.Z
                                     staging env
                                       │  смоук + ручная протыкка
                                       ▼  ручное подтверждение (prod-гейт)
                                     prod env   ← тот же :vX.Y.Z, без пересборки
```

1. **Разработка локально** — стенд `local/` (`docker compose up`).
2. **Тесты локально** — `cd node && deno test` + `bash test/integration.sh`.
3. **Push в `dev`** → CI: тесты и сборка `relay-node:<sha>` / `relay-caddy:<sha>`
   (sha-образ — быстрая итерация, не формальный релиз). Ноду CI не деплоит: боксы
   принимают SSH только с whitelist-адресов админа, адрес раннера в него не входит.
4. **Катим dev** — `bash scripts/deploy-relay-dev.sh`. Скрипт пинит
   `[env.dev].image_tag` в `wizard/environments.toml` на этот sha, запускает
   `wizard --node n1 deploy` (sync compose, pull, миграции из нового образа,
   `up -d`, `/health`), затем проверяет, что отвечает именно раскатываемая сборка.
   Пин надо закоммитить — по этому файлу история отвечает, какой образ на каком env.
5. **Проверка dev** — ручная протыкка. (`test/smoke.sh` постит `/waitlist` без
   ключа, поэтому годится только для env с `require_api_key = false`.)
6. **Merge `dev` → `main`** когда всё устраивает.
7. **Режем релиз** — ставим **ручной semver-тег `vX.Y.Z`** (или GitHub Release).
   CI собирает `relay-node:vX.Y.Z` / `relay-caddy:vX.Y.Z` **один раз** → ghcr.
8. **Катим `:vX.Y.Z` на staging** — пиним в `environments.toml`, затем
   `wizard --node n1 deploy`.
9. **Проверка staging** — ручная протыкка.
10. **Промоут того же `:vX.Y.Z` на prod** — визард требует `--confirm-prod` и
   чтобы `vX.Y.Z` был **опубликованным GitHub Release** (публикация = approve).
   Без пересборки.

## Правила

- **Иммутабельные версии.** Релизы пинятся по `:vX.Y.Z`, никогда `:latest`.
  Инвентарь каждого env пинит свой тег.
- **Пост-деплой проверка на каждом env.** Визард дёргает `/health` каждого env.
  Health говорит, что нода отвечает, но не что она новая, поэтому деплой ещё
  спрашивает то, что есть только в раскатываемой сборке —
  `scripts/deploy-relay-dev.sh` делает это запросом `POST /v1/client-error` без
  авторизации (401 на новой сборке, 404 на старой). `test/smoke.sh` постит
  `/waitlist` без ключа, так что годится только для env с
  `require_api_key = false` — то есть ни для dev, ни для staging, ни для prod.
- **Prod-гейт = опубликованный релиз.** Prod-деплой требует `--confirm-prod` И
  чтобы `image_tag` env был **опубликованным GitHub Release** `vX.Y.Z` (визард
  проверяет через API). Публикация релиза = approve — без инфры и раннера;
  непротестированный/недорелизнутый билд просто не доедет до prod.
- **Откат = задеплоить предыдущий `:vX.Y.Z`** на затронутом env (одной командой).
- **Release notes** на каждом GitHub Release.

## Env ↔ артефакт

| Env | Артефакт | Триггер | Гейт |
|-----|----------|---------|------|
| dev | `:<sha>` (ветка dev) | `scripts/deploy-relay-dev.sh` | зелёный CI |
| staging | `:vX.Y.Z` (релиз) | деплой тега | после зелёного dev |
| prod | **тот же** `:vX.Y.Z` | промоут тега | ручной approve |

Единственное, что push действительно деплоит сам, — панель: `deploy-dev.yml`
собирает её и заливает на CDN. Нода сама никогда не катится.

## Статус реализации

Регламент согласован 2026-07-16. **Сделано:** CI-сборки по тегам (`:<sha>` +
`:<branch>` при push, `:vX.Y.Z` при теге `v*`; без `:latest`); пин `image_tag`
per-env в `environments.toml` (`render` даёт `<repo>:<tag>`); гард prod-деплоя
(`--confirm-prod`); раскатка dev одной командой с проверкой живости
(`scripts/deploy-relay-dev.sh`); prod-гейт = `--confirm-prod` + проверка
опубликованного GitHub Release (`github.py`).

**Не сделано, и это стоит знать:** раскатка dev — команда, которую запускаешь ты,
а не шаг CI: боксы принимают SSH только с whitelist-адресов админа, и хостед-раннер
до них не достаёт. Self-hosted-раннер это закрыл бы — и он единственное, чего не
хватает для настоящего авто-деплоя dev.

`caddy_tag` по-прежнему **общий на весь пул** и лежит в незатрекованном
`inventory.toml`: один бокс не может крутить caddy, отличный от другого, а
`_guard_prod` его не проверяет — сдвинув его, сдвинешь и caddy в prod. У образов
ноды такой проблемы нет, они per-env.
