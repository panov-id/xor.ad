## Замеченные дефекты

**1. Мелочь: tools/check_jsonb_strings.ts:33.**
- Место: `FROM "${table_name}" WHERE jsonb_typeof("${column_name}")`. Двойная кавычка внутри имени не удваивается.
- Сценарий: эксперимент показал, что таблица `"we""ird"` даёт синтаксическую ошибку, то есть в SQL уходит «сырой» идентификатор. Вход приходит из `information_schema` (схема задаётся миграциями), а сам инструмент запускается только против тестовой БД в CI и `scripts/run-relay-database-tests.sh`. Атакующего входа нет, поэтому это не инъекция, а хрупкость.
- Исправление: `"${name.replaceAll('"', '""')}"`. Другой вариант — собрать запрос на стороне БД через `format('SELECT count(*) FROM %I WHERE jsonb_typeof(%I) = ''string''', table_name, column_name)`. Заодно стоит квалифицировать схему как `public.%I`: фильтр идёт по `table_schema='public'` (строка 23), а FROM разрешается через `search_path`.

**2. Мелочь, дефект дизайна аудита: db/046_unwrap_jsonb_strings.sql:14.**
- Сценарий: миграция переписывает `dsa_notices.snapshot`, то есть доказательную копию уведомления по ст. 16. После неё не остаётся следа, что строка менялась и когда. Хеша целостности и триггера неизменяемости на снимке нет (grep по `db/*.sql` не нашёл ни `TRIGGER`, ни хеша снимка), поэтому ломать нечего. Содержимое сохраняется без потерь: `JSON.stringify` не даёт дублей ключей, а смысл значений в эксперименте совпал. Меняется только представление и порядок ключей. При разбирательстве о доказательстве нельзя будет показать, что строка правилась, кроме как ссылкой на миграцию.
- Исправление: перед UPDATE сохранить затронутые id, например `INSERT INTO` в таблицу пометок или столбец `snapshot_rewritten_at`. Минимум — записать в миграции `RAISE NOTICE` с числом строк, а в журнале выката зафиксировать, сколько уведомлений затронуто на проде.

### 3. Мелочь: 046 обрывает выкат на строке, которая не является JSON
**Где:** `relay/node/db/046_unwrap_jsonb_strings.sql:14–17`, `relay/node/tools/migrate_db.ts:81–95` (одна транзакция на файл).

- мигратор старого образа сообщает о «лишних» записях в журнале миграций только как note (`src/lib/migration_order.ts:12–16`);
- старый код ожидал именно объекты, для него развёрнутые строки корректнее.
ПРОВЕРЕНО чтением.

**Как чинить.** Перед выкатом на p1 запустить read-only предпроверку для каждой колонки (на боксах Postgres 16, функция есть; ПРОВЕРЕНО в эксперименте):
