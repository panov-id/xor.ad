# Аудит: четыре независимых прохода по коду

Дата: 12 августа 2026. Ветка: `day29`.

Четыре прохода шли параллельно и не видели работы друг друга. Уровни: **спека
против кода**, **безопасность и модель угроз**, **выкат и эксплуатация**,
**корректность кода**. Ни один не имел права что-либо менять.

Где находку принесли независимо два или три прохода — это отмечено. Такие
надёжнее прочих: их видно с разных сторон.

**Что было запущено.** Только проход по корректности запускал код: `deno test`
в тринадцати конфигурациях, `deno check`, `deno lint`, вычислитель заголовков на
настоящем `panel/dist` — всё в одноразовых контейнерах с репозиторием на чтение.
Остальные три читали код и метаданные git. **Живьём не проверялось ничего:**
Bunny API не трогался, узлы не опрашивались, ни одна политика не открывалась в
браузере. Пункт 15 и весь раздел C выведены из схемы, а не из наблюдаемого
падения.

Помета **подтверждено** значит, что путь прослежен по коду до конца или
получен прогоном. **Предположено** — что вывод зависит от значения в проде или
от файла, которого проход не видел.

## A. Ломает выкат панели

Свежий, ни разу не работавший код: `deploy/panel-security-headers.mjs`,
`deploy/apply-edge-headers.py`, правки `deploy/deploy-panel-ci.sh` и
`.github/workflows/_deploy.yml`.

### A1. `deploy/__pycache__/` не игнорируется — подтверждено

След от проверки синтаксиса. Паттерна в `.gitignore` нет, попадёт в коммит по
`git add deploy/`.

### A2. Ни один `curl` не проверяет код ответа — подтверждено (выкат + безопасность)

`deploy/deploy-panel-ci.sh:43-47,65-66`, `deploy-landing.sh:153-157,250-251` в
обеих витринах. Нет `-f`, нет `-w '%{http_code}'`. `curl` без `--fail`
возвращает 0 на 401, 403, 500 и 507, поэтому `set -euo pipefail` здесь бесполезен.

Протухший `BUNNY_STORAGE_API_KEY` даёт `→ /index.html`, `cache purged.`,
`Panel deployed.` и зелёный прогон при неизменившейся зоне. Для панели хуже:
`deploy/bunny-panel-spa-fallback.sh:19` ставит `Custom404FilePath: /index.html`,
поэтому недозалитый `/assets/*.js` вернётся как HTML с кодом 200 — браузер
получит ошибку типа содержимого, панель покажет пустой экран, лог выката смолчит.

То же на сбросе кеша: политика применена, кеш не сброшен (401), лог говорит
`cache purged.` Край отдаёт старые файлы под новой политикой, хеши не совпадают,
панель не грузится, выкат зелёный.

### A3. Пустой `BUNNY_API_KEY` тихо выключает политику — подтверждено (выкат + безопасность)

`deploy-panel-ci.sh:54`, `deploy-landing.sh:185`. В GitHub Actions неопределённый
секрет разворачивается в пустую строку, а не в ошибку. Ветка `else` пишет одну
строку в stderr среди сотен `→ /path` и возвращает 0.

Дальше `PURGE_KEY="${BUNNY_API_KEY:-$BUNNY_STORAGE_API_KEY}"`
(`deploy-panel-ci.sh:23`) подставит ключ хранилища, которым
`POST /pullzone/{id}/purgeCache` не авторизуется, а A2 проглотит 401. Итог:
панель без заголовков, кеш не сброшен, статус — успех.

Контраст внутри одного файла: отсутствие `VITE_RELAY_API_URL` валит выкат через
`: "${VITE_RELAY_API_URL:?}"`, отсутствие политики — нет.

### A4. Правило ищется по префиксу описания — подтверждено (три прохода)

`deploy/apply-edge-headers.py:73-77` — `.startswith("security headers")`.
Соседние скрипты того же каталога сравнивают описание точным равенством:
`bunny-seo-index-redirect.sh:70`, `bunny-config-cache-rule.sh:64-65`.

Четыре следствия, все достижимые:

* Два правила с этим префиксом — `break` берёт первое в порядке ответа API
  (порядок не гарантирован), второе продолжает ставить свой заголовок. При двух
  `Content-Security-Policy` браузер применяет **пересечение**, и панель ломается
  тем сильнее, чем старше второе правило. Скрипт при этом печатает `updated`.
* Описание переименовали в интерфейсе Bunny — совпадения нет, `addOrUpdate`
  создаёт второе правило. Единственный сигнал — слово `created` вместо `updated`.
* Правило, заведённое руками с описанием вроде `security headers (temporary)`,
  будет молча перезаписано.
* `EdgeRules` отсутствует в ответе — `[]`, новое правило на каждый выкат.

### A5. `GET` не обёрнут, `POST` обёрнут — подтверждено (выкат + корректность)

`apply-edge-headers.py:73` вне `try`, при том что `POST` на `:81` обёрнут и даёт
внятное сообщение. 401, 403, 429 или 5xx дадут сырой traceback без упоминания
зоны — и убьют выкат ровно между заливкой файлов и сбросом кеша.

Там же: `.get("EdgeRules", [])` защищает от отсутствующего ключа, но не от
`"EdgeRules": null` — тогда `for item in None`. `urllib.error.URLError` (DNS,
таймаут) не ловится нигде. `json.loads(payload)["headers"]` (`:55`) даст
`KeyError` вместо сообщения.

### A6. Панель не печатает `counted` — подтверждено (выкат + корректность)

`panel-security-headers.mjs:102-111` считает `pages`, `inline_scripts`,
`inline_styles`, `style_attributes`, `relay`. `apply-edge-headers.py:55` читает
только `["headers"]` и `counted` выбрасывает. Лендинги печатают его —
`deploy-landing.sh:198`.

Прогон, где регулярка перестала находить инлайновый скрипт и `inline_scripts: 0`,
в логе выката выглядит ровно как правильный: уедет `script-src 'self'`,
применится успешно, панель умрёт. Это тот самый режим отказа, ради которого файл
написан.

### A7. Хеши style-атрибутов без `'unsafe-hashes'` — подтверждено

`panel-security-headers.mjs:84`. По CSP Level 3 хеш применяется к атрибуту
`style` только при наличии `'unsafe-hashes'` в директиве. В версии для лендингов
это учтено (`landing/security-headers.mjs:103`), в панельной — нет.

Сегодня безвредно: в `panel/dist` ноль атрибутов. Но первый же `style="…"` даст
скрипт, который отрапортует `style_attributes: 1`, выдаст хеш, который браузер
проигнорирует, и атрибут будет заблокирован. Сейчас это код, способный только
соврать: либо добавить `'unsafe-hashes'`, либо не собирать атрибуты вовсе.

### A8. Значение адреса реле не проверяется — подтверждено

`panel-security-headers.mjs:86` — `connect-src 'self' ${relay}` интерполяцией,
без `new URL()` и без сравнения с origin. Адрес с путём
(`https://relay.example/v1`) приложение переживёт — `panel/src/providers/api.ts:16`
клеит путь к строке, — а в CSP источник с путём без завершающей косой черты
матчится точным путём, и все запросы к `/v1/admin/...` окажутся заблокированы.

Отдельно: значение с пробелом и `;` допишет в заголовок собственные директивы.
Источник — секрет GitHub, то есть доверенный, поэтому это не эксплуатируемо; но
строка идёт в HTTP-заголовок без единой проверки.

### A9. Ни в одной политике нет `report-to` — подтверждено

Вся конструкция держится на утверждении из комментариев, что промах регулярки
«вылезет нарушением в консоли при первой же проверке после выката», то есть на
том, что человек откроет консоль. Политика при этом вычисляется на выкате и по
построению дрейфует. Приёмник уже есть — `POST /client-error`. Самое дешёвое
улучшение из всего списка: молчаливая поломка станет телеметрией.

## B. Безопасность прода

### B1. Env-файлы кладутся на узел без `chmod` — подтверждено

`relay/wizard/wizard.py:378-380`:

```python
def _write_remote(sftp, path: str, content: str) -> None:
    with sftp.file(path, "w") as fh:
        fh.write(content)
```

Файлы получают удалённый umask, обычно 0644. Этим методом кладутся
`compose/<env>.env` (несёт `SESSION_SECRET`, `RESEND_KEYS`,
`POSTGRES_PASSWORD` — `wizard.py:471-476`), `caddy.env` (`BUNNY_API_KEY`,
`ORIGIN_TOKEN`) и `backup.env`.

Тот же скрипт умеет иначе: `wizard.py:407` ставит `chmod 600` на
`authorized_keys`, `:410` — `chmod 440` на sudoers. Env-файлы просто пропустили.
Любой локальный аккаунт на узле читает `prod.env`.

### B2. `SESSION_SECRET` один на все среды, отзыва сессии нет — подтверждено по коду

`wizard.py:140` пишет одно и то же значение в `dev.env`, `staging.env` и
`prod.env`. `relay/node/src/lib/auth.ts:104-119` строит пользователя целиком из
claim'ов и запись `panel_users` не читает вовсе. `Claims` (`jwt.ts:29-35`) — это
`sub`, `role`, `brand`, `exp`: ни `iss`, ни `aud`, ни имени среды.

Три следствия:

1. Токен, выпущенный узлом dev, проходит проверку на prod побайтово. Dev —
   среда со слабее закрытым доступом.
2. `SESSION_TTL_S = 7 * 24 * 3600` (`auth.ts:31`), `jti` нет, сверки нет.
   Удалённый или понижённый оператор сохраняет полный доступ семь суток.
   Комментарий на `auth.ts:87-91` признаёт этот эффект для смены бренда, но не
   для удаления.
3. Компрометация секрета даёт платформенного админа: `brand: null` в
   `admin.ts:74-76,135-141` означает оператора, видящего все тенанты.

Развёрнут ли prod из того же `secrets.env` — **предположено**, проверяется одним
сравнением значений.

### B3. `deploy/.env.deploy` — режим 0664 — подтверждено

Девять живых ключей: `GITHUB_TOKEN`, `BUNNY_API_KEY`, `NAMECHEAP_API_KEY`, три
`RESEND_*`, три `IMPROVMX_*`. В git не отслеживается (`.gitignore:9`), история

`BUNNY_API_KEY` продублирован дословно в обоих файлах: одна ротация в двух местах.

### B4. Ключи передаются аргументами командной строки — подтверждено

`apply-edge-headers.py:50` и вызов в `deploy-panel-ci.sh:58`; то же в
`bunny-api-cutover.sh:27`, `bunny-api-origin-token.sh:28` (там аргумент —

### B5. Origin-allowlist не является границей авторизации — подтверждено

`relay/node/src/lib/api_key.ts:82-90`. Шапка файла утверждает, что украденный
ключ бесполезен с другого сайта. Вне браузера `Origin` — обычный заголовок, а
publishable-ключ намеренно лежит в `config.js` каждого лендинга.

Что превращает это из мусора в аналитике в отказ обслуживания:

* `/pageview` не имеет ограничения по адресу вообще — среди `routes/*.ts`
  `rate_limit` импортируют только `report.ts`, `waitlist.ts`, `v1.ts`.
* Дневная квота — один счётчик `EVENTS` на ключ, общий для всех публичных
  маршрутов (`lib/quota.ts:23,50,97-124`). Исчерпав его через `/pageview`,
  нападающий получает `429` на `/waitlist` жертвы до полуночи UTC: форма
  регистрации чужого бренда перестаёт принимать заявки.
* Тем же ключом пишутся лиды в чужое хранилище с отправкой приветственного
  письма от домена и аккаунта Resend жертвы (`waitlist.ts:127-133`), и
  подкладываются уведомления в её очередь по ст. 16 с произвольным
  `notifier_email`, на который затем пишет модератор тенанта.

Комментарий `tenant.ts:99-107` описывает ровно этот сценарий, но применяет вывод
только к нативным ключам.

### B6. Снимок DSA берётся по клиентскому id без фильтра по тенанту — подтверждено, латентно

`lib/dsa_snapshot.ts:62-87` — `SELECT ${columns} FROM ${table} WHERE id = $1`,
где `targetId` приходит прямо из публичного тела (`routes/report.ts:103`), а
результат кладётся в уведомление под брендом заявителя.

С ключом тенанта A (или через B5) отправить `/report` с `target_kind:
"feed_message"` и `target_id` тенанта B: поля `text`, `created_at`,
`author_identity` копируются в уведомление A, где фильтр `brand` указывает уже на
A.

Сегодня не стреляет: `tableExists()` возвращает `not_accessible`, пока
`feed_messages` и `offers` не созданы. **Граница откроется молча в день их
появления** — чинить надо до, а не после. Комментарий на `:63-65` фиксирует
решение «искать по id, не по тенанту» как осознанное.

Заодно `kind in SNAPSHOTTABLE` (`:76`) стоит заменить на `Object.hasOwn`:
`"constructor" in SNAPSHOTTABLE` истинно, и сегодня это недостижимо только
благодаря `KINDS` в `report.ts:20`.

## C. Узел

### C1. `dsa_statements.brand NOT NULL` остался — подтверждено по схеме

`db/007_dsa_notice_unattributed.sql` снял ограничение только с
`dsa_notices.brand`; `dsa_statements.brand text NOT NULL` (`db/005:63`) не тронут.
`routes/dsa.ts:157-165` вставляет туда `notice.brand`.

Неатрибутированное уведомление может решить только оператор платформы
(`dsa.ts:130`), и этот единственный путь ведёт прямо в дефект: вставка падает,
statement не создан, `decided_at` остался пустым, заявителю ничего не ушло,
ответ 500. Тип `NoticeRow.brand: string` (`dsa.ts:24`) врёт про nullable-колонку,
поэтому `deno check` молчит.

**Слова `upheld` нет ни в одном файле в `test/`.** Весь путь удовлетворённого
уведомления — вставка statement, письмо автору, `delivered_at` — не исполняется
ни одним тестом.

### C2. Двойное решение закрыто только для последовательного случая — подтверждено

`dsa.ts:133` читает `decided_at`, `dsa.ts:186-189` пишет без
`AND decided_at IS NULL`. Два одновременных POST проходят гард оба, вставляют по
statement, шлют по паре писем, и второй `UPDATE` молча заменяет первое решение.
Комментарий на `dsa.ts:112-113` утверждает, что это починено.

Смежное: цепочка INSERT → письмо → `UPDATE delivered_at` → `UPDATE dsa_notices`
не в транзакции. Падение после первого шага оставляет statement без решённого
уведомления.

### C3. Ответ заявителю умеет два исхода из четырёх — подтверждено

`docs/dsa/SPEC_RU.md:225` требует сообщать: удалено, оставлено, контента уже не
было, недоступно. `dsa.ts:284` принимает только `upheld|rejected`,
`db/006_dsa_snapshot_state.sql` сузил `status` до четырёх значений без
`gone`/`not_accessible`, письмо (`mailer.ts:207-215`) знает две формулировки, а
`snapshot_state` заявителю не уходит вовсе.

По истёкшей фразе человек получит «мы не согласились с вашим сообщением» вместо
«контента уже не было» — ровно та ложь, против которой написан комментарий в
`dsa_snapshot.ts:16`.

### C4. Карты в памяти не чистятся — подтверждено

`lib/tenant.ts:20` — `keylessNoticedAt` ключуется как `${brand}|${origin}` и не
удаляет записей никогда. При `require_api_key = false` перебор заголовка `Origin`
даёт новую запись и, поскольку `last = 0`, новую строку `warn` на **каждый**
запрос; `warn` копируется в хранилище (`shouldPersist`). Комментарий на
`:14-18` обещает одну строку на вызывающего в час.

`lib/quota.ts:26,28` — `pending` и `totals` ключуются с датой, вчерашние ячейки
не удаляются никогда.

### C5. `mailer.ts:253` — `targetKind` не используется — подтверждено `deno lint`

`whatWasRestricted` различает контент исключительно по именам полей строки
(`row.text` против `row.offer_text`, `row.created_at` против `row.published_at`),
а первый аргумент игнорирует.

Следствие для тестов: в `test/statement_of_reasons.test.ts` случаи на строках 15
и 28 отличаются только этим игнорируемым аргументом. Хуже: фикстура оффера на
`:31` передаёт `created_at`, которого настоящий снимок оффера не содержит —
`SNAPSHOTTABLE.offer.columns` (`dsa_snapshot.ts:49`) это
`id, offer_text, discount_value, conditions, published_at, venue_id`. Ветка
`published_at`, единственная работающая в бою, не покрыта ничем, а тест зелёный
на данных, которых боевой путь не производит.

### C6. Мелкие — подтверждено

* `dsa.ts` — `status = 'in_review'` недостижим: значение есть в схеме, очередь по
  нему фильтрует (`:219`), ни один маршрут его не выставляет.
* `api_key.ts:155-166` — `revokePublishableKey` в ветке базы не зовёт

* `v1.ts:14` — мёртвый импорт `readJson`.
* `dsa_snapshot.ts:76` — неизвестный вид цели получает `received` («копия не
  потребовалась») вместо `not_accessible` («поверхность не построена»). Сегодня
  верно для `other`; добавление пятого вида в `KINDS` без строки в
  `SNAPSHOTTABLE` начнёт врать молча.
* `report.ts:143` — `rows[0]?.id ?? null` при пустом массиве даст квитанцию с
  `id: null` и ответ `202 {ok: true}`. Для `INSERT … RETURNING` маловероятно —
  **предположено**.
* `report.ts:103` — `text(body.target_id, 200)` молча обрезает идентификатор.
  Обрезанный не найдётся, и уведомление получит `target_gone` («истекло») вместо
  «прислали мусор» — ровно то различие, которое защищает весь `dsa_snapshot.ts`.

**Направление отказа у регулярок правильное.** Все четыре шаблона прогнаны по
настоящим страницам: `panel/dist/index.html` — 1 из 1 инлайновых скриптов
(внешний с `src=` отсеян верно), `neighbro/index.html` — 4 из 4
(`type="application/ld+json"` пропущен верно), остальные страницы — тоже без
