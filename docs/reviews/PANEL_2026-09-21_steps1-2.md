## Опровержения

Существенные находки отданы второму агенту с заданием их **опровергнуть**.
По умолчанию — «опровергнута», если опровергающий не уверен. Ниже вердикты
как вернул опровергающий; опровергнутое остаётся в файле, чтобы через месяц
ту же находку не открыли заново.

### Круг 1 — критичное по безопасности и откат образа

**A. Трилатерация центра фразы — ПОДТВЕРЖДЕНА.** `feed.ts:283-287` считает
`sqrt(pow((f.lat-$12)*111320,2)+…) <= f.area_radius + $14` по точным
координатам; `feed.ts:200-212` берёт `lat`/`lon` как `Number(...)` из query
без квантования, проверяется только диапазон и `radius ∈ [100, RADIUS_CEILING]`;
`feed.ts:306-312` отдаёт наружу `area_radius` в явном виде, то есть правая
часть неравенства зрителю известна; `quantise` — детерминированное округление
без соли и джиттера. Предела частоты на `GET /feed` нет: `checkAll` в
`routes/feed.ts` не вызывается ни разу (в `client_error`, `identity`,
`pageview`, `waitlist`, `auth`, `transfer`, `csp_report`, `v1`, `report`,
`admin` — вызывается). Оговорка опровергающего в пользу находки: расширение
радиуса размывает границу только при пустой выдаче, а зритель задаёт `radius`
так, чтобы выдача была непустой, либо ставит курсор `after`, при котором цикл
не расширяется (`feed.ts:279`).

**B. Оракул бумажного кода — ПОДТВЕРЖДЕНА.** `identity.ts:409-416` —
`caller = signed instanceof Response ? null : signed`, своя живая сессия даёт
`caller != null`; `identity.ts:436-443` — проверка ключей целиком внутри
`if (!caller)`; поиск идёт после (`:445-451`); промах даёт `countMiss()` и 404
(`:457-470`); `sameDevice` считается после поиска (`:473`) и для чужого кода
всегда false; попадание уходит в `identity.ts:510` → INSERT с
`body.sign_pub = undefined` при `sign_public_key text NOT NULL`
(`db/022:120`) → catch (`:548`) → 503, и `countMiss()` не вызывается.
Опровергающий добавил к находке: до падения в той же транзакции выполняются
`freezeSession` и `burnShare` по всем живым сессиям жертвы
(`identity.ts:519-529`), но транзакция откатывается — это оракул, а не
разрушение. Тормоза находку не ломают: `pausedFor()` (`identity.ts:382-391`)
считает только промахи, `RECOVERY_CLAIM_LIMITS` 10/час и 30/сутки на адрес
(`rate_limit.ts:145-148`) для подтверждения одного сфотографированного кода с
избытком.

**C. ПИН в `POST /sessions/invite` мимо счётчика — ПОДТВЕРЖДЕНА.**
`transfer.ts:88-103`: SELECT выбирает только `auth_hash, locked_at` (`:90-93`),
значит `attempts_left` и `next_attempt_at` нечем ни прочитать, ни списать;
заморозки на десятой нет; сравнение `!==` не постоянного времени против
`sameHash` (`identity.ts:588-593`). Защиты выше по стеку нет: `checkAll` в
`transfer.ts` зовётся только на `:147` и `:227`, `createInvite` (`:374`) идёт
без предела по адресу, а `callerOf` счётчиков ПИНа не знает. Комментарий
`transfer.ts:69-73` обещает ровно обратное: «A stolen signing key alone must
not be able to start a transfer».

**D. Вычисление точного возраста автора — ПОДТВЕРЖДЕНА с поправкой.**
Симметрия совпадает в обеих реализациях: `feed_geo.ts:78-93` и SQL
`feed.ts:251-259` (`CASE WHEN a.age <= 20 THEN $5 BETWEEN greatest(13, a.age-2)
AND a.age+2 ELSE $5 >= least(21, a.age-2) END`) — это буквально `band()` в SQL,
шума и асимметрии нет. Поправка опровергающего: середина множества равна `a`
только внутри 15…18, на краях отрезок обрезается — но усечённое множество само
однозначно определяет `a`, так что находка не ослабевает. Возраст —
самозаявленное целое без проверки (`identity.ts:137-148`), пять личностей —
половина часового предела с одного адреса (`rate_limit.ts:137-140`).

**E. Откат образа убивает цепочку подметальщика — ОПРОВЕРГНУТА.** Надгробие
исключено из обоих мест, где могло бы мешать: `enqueueOnce` читает
`WHERE kind = $1 AND locked_until IS DISTINCT FROM 'infinity'`
(`jobs.ts:100-105`), и частичный уникальный индекс объявлен с тем же условием
(`db/020_jobs_lease.sql:14-16`, с комментарием про этот самый дефект от
07.09.2026). `armScheduledJobs()` (`scheduled.ts:181-192`) на старте
переставляет все девять видов. Остаётся мусорная строка и запись `last_error`,
а не конец цепочки. Автор находки пришёл к тому же выводу сам по ходу разбора.
В доклад находка не идёт ни строкой. Что в ней пережило — отдельное
наблюдение: в течение отката `sweep_feed_expired` не работает и просроченные
фразы лежат читаемым текстом, о чём не говорит ни лог, ни тревога.

### Круг 2 — данные, протоколы, согласованность

**F. Курсор ленты роняет строки внутри миллисекунды — ПОДТВЕРЖДЕНА прогоном.**
Опровергающий поднял временный `postgres:16-alpine` и вставил три строки
`.500900`, `.500123`, `.499000` в одну миллисекунду. Страница 1 (LIMIT 1)
отдала `.500900`; усечённый курсор дал `10:00:00.500`; страница 2 с предикатом
из `feed.ts:280` вернула только `.499000`. Строка `.500123` не попала ни на
одну страницу. Квантования при вставке нет: `visible_at` ставится как
`SET visible_at = now()` в `feed_verdict.ts:publishPhrase`, значения по
умолчанию у колонки нет. Достижимость: нужны две публикации, чьи `now()` попали
в одну миллисекунду, и граница страницы ровно там — редко, но ничем не закрыто.
Комментарий `feed.ts:222-224` заявляет, что пара `(visible_at, id)` заведена
именно против потери на границе: она закрывает совпадение в пределах
миллисекунды, но не внутри неё. Контейнер и скрипт убраны за собой.

**G. `identity_stats` без бэкфилла — ЧАСТИЧНО.** Механизм подтверждён:
в `db/025` нет ни одного `INSERT … SELECT`, единственный писатель —

**Опровергнута вторая половина** — «на dev могли остаться личности без строки»:

**H. `lang = 'und'` против фильтра языков — ЧАСТИЧНО.** Механизм подтверждён

ПРОВЕРЕНО ведущим: `grep -c 'route("PATCH"|route("PUT"' routes/identity.ts` —

**I. У `GET /feed/density` нет предела частоты — ПОДТВЕРЖДЕНА.**

курсор ленты теряет микросекунды (F, прогон); нет предела на `GET /feed` и на

дашборд не знают ни одной метрики ленты и переноса; датчик паузы пишется только
на запросе; правило «удержание» в `feed_limits.ts` неотличимо от «одна за раз»;
`density()` не применяет фильтры зрителя, хотя комментарий обещает обратное.

страница описаны без `lang`, `farther_than_asked`, `radius_used`.

**Мелочь.** 401 без `WWW-Authenticate`; 503 без `Retry-After`; 204 мимо
