## Сделано 05.08.2026 (серверная часть)

- [x] **Таблицы** `dsa_notices` и `dsa_statements` — миграция
      `relay/node/db/005_dsa_notices.sql`. Проверки прямо в схеме: обоснование
      непустое, `bona_fide` обязан быть true, имя и почта nullable ради
      исключения §5.1.
- [x] **Эндпоинт** `POST /report` — `relay/node/src/routes/report.ts`, публичный
      и без авторизации: орган или посторонний должны дотянуться без аккаунта.
- [x] **Слепок** — `relay/node/src/lib/dsa_snapshot.ts`. Снимается в момент
      поступления. Возвращает **три** состояния: скопировано, `target_gone`,
      `not_accessible`. Третье — чат (не хранится) и поверхности, которых ещё
      нет в базе; сказать «истекло» вместо «не смотрели» было бы враньём.
- [x] **Подтверждение получения** — `sendNoticeReceipt` в `lib/mailer.ts`,
      ст. 16(4), best-effort: письмо не должно терять уведомление.
- [x] **Удаление через год** — `tools/prune_dsa_records.ts` + задание `PRUNE_DSA`
      в `lib/scheduled.ts`, рядом с уборкой просмотров.
- [x] Типы проверены в контейнере: `docker run --rm -v "$PWD:/app" -w /app
      denoland/deno:2.1.4 deno check src/main.ts`.

## До запуска — осталось

- [ ] **Форма `report.html`** на обеих витринах: поля из SPEC §3, отдельный путь
      без имени и почты для случая §5.1. Без неё эндпоинт есть, а прийти к нему
      человеку неоткуда — это и есть требование ст. 16(1) «лёгкий доступ».
      **Решить при старте:** язык формы. Юридические страницы EN-only по
      решению, форма — интерфейс; либо повторить EN-only, либо переводить на
      17 и 10 локалей.
- [ ] **Ссылка на форму** в футере и на юридических страницах обеих витрин
- [ ] **Экран разбора в панели**: очередь по `status IN ('received','in_review')`,
      слепок, решение, отправка обоих писем. Индекс `dsa_notices_queue` уже под
      это заточен.
- [ ] **Шаблоны двух писем**: ответ заявителю (ст. 16(5) — что решено, почему,
      участвовала ли автоматика, пути обжалования) и мотивировка автору
      (ст. 17(3) — семь элементов, личность заявителя **не раскрывать**)
- [ ] **RLS на обе таблицы**: заявитель видит только своё уведомление, автор —
      только свою мотивировку
- [ ] **Ссылка на форму** в футере и на юридических страницах обеих витрин —
      механизм обязан быть «лёгким в доступе» (ст. 16(1))
- [ ] **Шаблоны писем**: подтверждение получения, ответ заявителю, мотивировка
      автору, отказ по жалобе на качество услуги. Каждый — с обязательными
      элементами из SPEC §6 и §7
- [ ] **Уведомление о существенных изменениях** документов. Условия и политика
      сами обещают «signposted in the Service», ст. 14(6) требует того же.
      Механизма нет: нужен баннер или экран при первом входе после правки
