# API-платформа: публичный API, вебхуки, нотификации, очереди

Черновик для обсуждения. Ничего не реализовано — это карта развилок и цена каждой.
Решения принимаются до кода, потому что одна из них меняет архитектуру узла целиком
(см. «Центральное напряжение»).

## Что уже есть

| Кусок | Состояние |
| --- | --- |
| HTTP-узел | Deno, свой роутер, `POST /waitlist`, `POST /client-error`, `GET /health`, `GET /metrics` |
| Чат | слот-заглушка `GET /chat` → 501 |
| Хранилище | абстракция «объект = запись»: Bunny Storage на пуле, `fs` на локальном стенде |
| Почта | Resend (по бренду) / SMTP на стенде |
| Панель | Refine + magic-link сессии, RBAC-ядро `access/`, audit-журнал, исследователь логов |
| Наблюдаемость | структурный JSON-лог в stdout, счётчики Prometheus |

Ключевое свойство текущего узла: **он не хранит состояние сам**. Всё состояние —
в объектном хранилище, узлы идентичны и взаимозаменяемы. Отсюда все ограничения ниже.

## Центральное напряжение

Очередь — это состояние с блокировками: «взять задачу, никому больше не отдавать,
через N секунд вернуть в строй, если не подтвердили». Объектное хранилище такого не
умеет: нет атомарного compare-and-swap, нет аренды, `list` не консистентен.

Значит любая честная очередь означает **новое хранилище состояния** рядом с узлом.
Это первая и главная развилка — всё остальное (вебхуки, нотификации, ретраи) от неё
зависит, потому что доставка вебхука без очереди с ретраями — это не доставка.

Варианты в порядке роста цены:

| Вариант | Что даёт | Чем платим |
| --- | --- | --- |
| **Без очереди**, отправка в процессе запроса | ноль инфраструктуры | потеря события при сбое, нет ретраев, медленные ответы |
| **Postgres (уже есть Supabase)** — таблица задач + `SELECT … FOR UPDATE SKIP LOCKED` | транзакции, ретраи, DLQ, видно в SQL | узел перестаёт быть stateless-над-объектами; нужна связность с БД из пула |
| **Redis/Valkey рядом с пулом** | быстрые очереди, стримы, TTL | ещё один сервис в проде, персистентность настраивать отдельно |
| **Внешняя очередь** (QStash / Cloudflare Queues) | ретраи и расписания «из коробки», узлы остаются stateless | внешняя зависимость, лимиты, данные ходят наружу |
| **Deno KV** на узле | ноль внешних сервисов | локально для узла, между узлами пула не шарится — для пула не годится |

Предварительная рекомендация: **Postgres**, потому что Supabase уже в инфраструктуре
и это единственный вариант, где очередь, подписки на вебхуки и журнал доставок живут
в одном месте и запрашиваются по-человечески. Но это осознанный отказ от идеи
«узел ничего не знает, кроме объектов» — обсуждаем.

## 0. Мультитенантность: сторонние разработчики как бренды

Решено: потребитель платформы — **третьи стороны**. Сторонний разработчик подключает
свой домен как бренд и получает полный бэкенд: приём событий, транзакционную почту со
своего домена, вебхуки наружу и **отдельный вход в панель** со своими пользователями,
ролями, audit-журналом и исследователем логов — всё в границах своего бренда.

Это решает открытые вопросы 2, 3 и 4 разом: ключи, лимиты и внешняя документация
становятся обязательными, вебхуки клиентские (значит UI подписок, ротация секретов,
SLA на доставку), нотификации нужны обоих видов — операторские алерты и продуктовые.

**Что уже готово под это.** Бренд — не новое понятие: `Brand { key, name, domain,
from, match[] }` в `relay/node/src/config.ts` добавляется через env `BRANDS` без правки
кода, а почта уже пер-брендовая (`RESEND_KEYS_BY_BRAND` — свой аккаунт и свой домен
отправителя на бренд). Самая дорогая часть предложения — «письма уходят от тебя, а не
от нас» — работает сегодня.

**Чего нет.** Бренд сейчас — ярлык, а не граница данных, и в таком виде наружу его
отдавать нельзя:

```ts
// routes/waitlist.ts — бренд приходит из тела запроса, его выбирает клиент
const brandHint = typeof body.brand === "string" ? body.brand : undefined;

// …но в ключе объекта бренда нет: пространство имён общее на всех
const key = `waitlist/${config.envName}/${await sha256hex(email)}.json`;
```

Отсюда два следствия, каждое фатально для арендатора: **дедуп глобальный** (email,
записавшийся у арендатора A, для арендатора B уже «дубликат», и лид молча теряется),
и **изоляции нет** (в теле запроса можно назвать любой чужой бренд).

**Форма решения.** Бренд уезжает в префикс ключа, а его значение берётся из субъекта
запроса, а не из тела:

```ts
// было
const key = `waitlist/${config.envName}/${await sha256hex(email)}.json`;

// стало — арендатор в префиксе, дедуп внутри арендатора
const key = `${subject.brand}/waitlist/${config.envName}/${await sha256hex(email)}.json`;
```

Субъект несёт бренд в обоих видах, а `null` означает оператора платформы, который
видит всё:

```ts
export type AccessSubject =
  | { kind: "user"; role: Role; brand: string | null }
  | { kind: "key";  scopes: readonly Permission[]; brand: string };
```

Важно: `can()` отвечает на вопрос «можно ли действие», а тенантность — это второй
вопрос, «над чьими данными», и он не решается добавлением фильтра в роуты. Одно
забытое место на чтении — утечка между арендаторами. Поэтому доступ к хранилищу
проходит через слой, который физически не умеет вернуть чужой префикс:

```ts
function scoped(subject: AccessSubject) {
  const prefix = subject.brand ? `${subject.brand}/` : "";
  return {
    put:  (path: string, body: unknown) => storage.put(prefix + path, body),
    get:  (path: string) => storage.get(prefix + path),
    list: (prefix2: string) => storage.list(prefix + prefix2),
  };
}
```

Ключ API получает владельца и квоту:

```ts
interface ApiKey {
  id: string;
  hash: string;
  brand: string;          // арендатор; жёстко ограничивает область ключа
  scopes: Permission[];
  quota: { events_per_day: number; webhooks_per_day: number };
  // …остальные поля — см. раздел 1
}
```

**Что это добавляет к списку работ.** Две вещи, которых в разделах ниже нет вовсе:
*подключение арендатора* и *квоты с биллингом* (счётчик на ключ, общий на весь пул —
в объектном хранилище не живёт).

**Самостоятельной регистрации не будет — решено 29.07.2026.** Арендатора заводит
только админ платформы: создаёт бренд, затем оператора внутри этого бренда, и узел
шлёт приглашение на почту. Причина в том, что бренд здесь — граница данных, а не
строка в анкете: открытая форма регистрации означала бы, что незнакомый человек
одним нажатием создаёт себе пространство имён, ключи и вход в панель, а платформа
узнаёт об этом постфактум. Пока арендаторов заводят по одному и по договорённости,
приглашение честнее описывает то, что происходит на самом деле.

Приглашение — тот же одноразовый токен, что и обычная ссылка входа, но живёт семь
дней вместо пятнадцати минут: письмо читают из почты на следующий день, а не в ту же
минуту. Повторная отправка — `POST /admin/panel-users/:email/invite`, в тех же
границах видимости: арендатор не может пригласить в чужой бренд.

## 1. Публичный API

Сейчас эндпоинты плоские и без версии. Публичный API это фиксирует навсегда, поэтому
сначала форма, потом содержание.

**Версионирование.** Префикс `/v1/…`. Существующие `POST /waitlist` и
`POST /client-error` остаются как есть (их зовут лендинги) и алиасятся на `/v1`.

**Аутентификация.** Панельный JWT — для людей. Для машин — ключи:

```ts
// Ключ показывается один раз при создании; хранится только хэш.
interface ApiKey {
  id: string;            // "ak_live_7f3c…" — префикс виден в панели и в логах
  hash: string;          // sha256 секрета
  name: string;          // "sosed.place landing"
  scopes: Permission[];  // те же строки, что и в ядре access/
  created_by: string;
  created_at: string;
  last_used_at: string | null;
  revoked_at: string | null;
}
```

Важно: **скоупы ключа — те же пермишены, что у ролей**. Ядро `access/` уже отвечает на
вопрос «можно ли», и `AccessSubject` расширяется вторым видом субъекта без изменения
контракта `can()`:

```ts
export type AccessSubject =
  | { kind: "user"; role: Role }
  | { kind: "key"; scopes: readonly Permission[] };
```

**Ошибки.** Одна форма на все ответы:

```json
{ "error": { "code": "rate_limited", "message": "…", "request_id": "…", "retry_after": 30 } }
```

**Идемпотентность.** Заголовок `Idempotency-Key` на всех POST: ключ + хэш тела →
сохранённый ответ, повтор возвращает тот же результат. Без этого ретраи клиента
плодят дубли.

**Пагинация.** Курсорная, ровно как уже сделано в логах (`before` + `limit`), а не
offset — в объектном хранилище offset не имеет смысла.

**Rate limiting.** Счётчик на ключ и на IP. Без общего состояния лимит будет
пер-узловой (то есть при N узлах фактический лимит ×N) — ещё один аргумент в пользу
общего хранилища.

## 2. Исходящие вебхуки

Подписка:

```ts
interface WebhookSubscription {
  id: string;
  url: string;
  events: string[];        // "waitlist.created", "panel_users.role_changed", "*"
  secret: string;          // для подписи; показывается один раз
  active: boolean;
  created_at: string;
}
```

**Подпись.** HMAC-SHA256 по `timestamp.body`, заголовки
`X-Xor-Signature: v1=<hex>` и `X-Xor-Timestamp`. Приёмник обязан отвергать старые
таймстемпы — иначе подпись не защищает от повтора.

**Доставка.** Пробуем один раз синхронно? Нет: доставка обязана быть асинхронной,
иначе тормозной подписчик тормозит наш API. Отсюда очередь (см. выше) с ретраями
`1м → 5м → 30м → 2ч → 6ч`, после исчерпания — dead-letter.

**Журнал доставок** — то же, что audit-журнал: одна запись на попытку, и страница в
панели поверх готового `LogExplorer` (окно, гистограмма, курсор — уже написаны).
Кнопка «повторить» на записи.

**События первой очереди:** `waitlist.created`, `client_error.received`,
`panel_user.created` / `.role_changed` / `.deleted`. Все три последних уже пишутся в
audit — вебхук становится вторым потребителем того же события.

## 3. Входящие вебхуки

Приём чужих событий (Resend — доставка/бounce/жалоба; платежи, если появятся):

- проверка подписи провайдера **до** разбора тела;
- идемпотентность по идентификатору события провайдера;
- быстрый `2xx`, обработка — в очередь.

Ближайшая польза: события Resend закрывают вопрос «дошло ли письмо» — сейчас на него
ответа нет вообще.

## 4. Нотификации

| Канал | Состояние | Что нужно |
| --- | --- | --- |
| Email | работает (Resend, по брендам) | шаблоны отвязать от кода приветствия |
| Web push | есть черновик `docs/pwa-push_*.md` | VAPID-ключи, хранение подписок, отправка из очереди |
| В панели | нет | лента событий из audit + доставок; дешевле всего |
| Telegram | нет | бот-токен, чат-ид; удобно для алертов дежурному |

Развилка: нотификации — это **отдельный слой над очередью** (шаблон + канал +
получатель + предпочтения), а не «ещё один вызов Resend в роуте». Иначе каждое новое
событие снова руками рассылается по каналам.

## 5. Очереди — форма задачи

```ts
interface Job {
  id: string;
  kind: string;            // "webhook.deliver" | "email.send" | "push.send"
  payload: unknown;
  run_at: string;          // отложенный запуск и backoff
  attempts: number;
  max_attempts: number;
  locked_until: string | null;  // аренда воркера
  last_error: string | null;
  created_at: string;
}
```

Воркер: отдельный процесс в том же образе (`deno run worker.ts`), берёт задачи
батчем, продлевает аренду, при падении задача возвращается сама по истечении аренды.
На пуле — по воркеру на узел, конкуренция решается блокировкой в БД.

Панель: глубина очереди, возраст самой старой задачи, DLQ, кнопка «повторить».
Метрики Prometheus: `queue_depth`, `job_attempts_total`, `job_duration_seconds`.

## 6. Права

Ядро `access/` расширяется строками, роли — картой. Ничего в `can()` не меняется:

```ts
"api_keys.read", "api_keys.write",
"webhooks.read", "webhooks.write", "webhooks.replay",
"queues.read", "queues.manage",
```

Правило из ядра остаётся: неизвестная пара ресурс/действие в панели **запрещается**,
так что новая страница без решения о праве не откроется ни у кого.

## 7. Порядок, если делать

1. **Тенантность** (раздел 0): бренд в ключах хранилища, `brand` в `AccessSubject`,
   `scoped()`-слой доступа, миграция существующих объектов.
2. API-ключи: хранение хэша, скоупы, владелец-бренд; `/v1` с идемпотентностью.
3. Хранилище состояния (решение из «Центрального напряжения») + квоты, лимиты,
   таблица задач и воркер.
4. Исходящие вебхуки поверх очереди: подписки, подпись, ретраи, журнал доставок.
5. Панель арендатора: вход, свои пользователи, ключи, подписки, доставки, очередь
   (все страницы — поверх `LogExplorer`). Регистрации бренда здесь нет: его заводит
   платформа и приглашает арендатора письмом (см. раздел 0).
6. Входящие вебхуки Resend → статусы писем.
7. Слой нотификаций (email + в панели), затем web push.

Тенантность стоит первой намеренно, вопреки соблазну начать с очереди: она
переписывает раскладку ключей в хранилище, а очередь, журнал доставок и квоты живут
уже поверх неё. В обратном порядке всё это придётся мигрировать второй раз.

## Открытые вопросы

1. ~~Куда переезжает состояние~~ — решено 28.07.2026: **свой Postgres рядом с
   узлом**, только под управляющее состояние (ключи, бренды, квоты, очередь,
   идемпотентность, агрегаты). Данные — лиды, просмотры, ошибки, логи — остаются
   в объектном хранилище. Разбор и основания: `state-decision_RU.md`.
2. ~~Кто потребитель публичного API~~ — решено: третьи стороны, полный BaaS с
   отдельным входом в панель (раздел 0). Отсюда: 3 — вебхуки клиентские, 4 —
   нотификации нужны обоих видов.
5. **Остаётся ли узел взаимозаменяемым** — пока да, но с оговоркой. Узел
   по-прежнему не хранит состояния сам; база живёт рядом с ним на том же боксе.
   Это работает, **пока на среду приходится один бокс**. Второй бокс той же среды
   поднял бы вторую базу и молча расщепил состояние, поэтому визард такую
   конфигурацию отклоняет. Настоящий ответ понадобится, когда пул реально
   вырастет: либо одна база на среду по сети, либо managed.
