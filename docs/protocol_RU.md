# Протокол: контракт между клиентом и узлом

Спека чата (`chat_RU.md`) описывает **что** происходит, схемы потоков
(`chat-flows_RU.md`) — **как это движется**, карта тестов (`test-map_RU.md`) —
**чем доказывать**. Здесь четвёртое: **по каким проводам это идёт**.

Документ заведён 28.08.2026 и появился по счёту, а не по вкусу: спека называет
**шесть** маршрутов, разбросанных по восьми разделам, а операций в ней описано
втрое больше. По §13 первым пишется терминальный клиент — ровно затем, чтобы
протокол стал проверяемым; но проверять нечего, пока он не собран в одном месте.

## Как читать: два сорта строк

В таблицах маршрутов у каждой строки есть **происхождение**, и его надо читать
первым:

| Метка | Что значит |
|---|---|
| **спека** | маршрут назван в `chat_RU.md` или в схемах потоков; здесь он только собран |
| **предложено** | операция в спеке описана, а имени у неё не было; имя дано **здесь** и требует согласия |

Разделение не формальность. Правило проекта запрещает выдумывать поля API и
поведение эндпоинтов; отличить собранное от предложенного — единственный честный
способ написать этот документ, не нарушив его.

## 1. Общее

- **Транспорт:** HTTPS для запросов, WebSocket для доставки. Сокет нужен только
  чату и столу; лента, лайки и мэтчи живут на запросах.
- **Формат:** JSON в теле, UTF-8. Двоичного протокола нет и не планируется.
- **Время:** unix-секунды, UTC. Часовых поясов в протоколе нет нигде.
- **Идентификаторов пользователя наружу не уходит ни одного** (§8.11): клиент
  знает ровно два вида uuid — фразы в ленте и чата.

## 2. Подпись запроса — из спеки, дословно

```
подписывается   <метод>\n<путь>\n<sha256 тела>\n<unix-время>
заголовки       x-identity-session   uuid живой сессии
                x-identity-time      то же время, что в строке
                x-identity-sign      подпись, base64url
окно            ±5 минут
алгоритм        ECDSA, namedCurve P-256, hash SHA-256
```

- **Тело входит хэшем, а не целиком** — иначе подпись считалась бы по потоку.
- **Путь входит без строки запроса**: в ней может оказаться что угодно, а подпись
  обязана быть воспроизводимой.
- **Окно вместо nonce** — сознательный размен (§8.2): перехвативший запрос может
  повторить его внутри пяти минут; nonce потребовал бы общей памяти узлов.

## 3. Лицо, версия и совместимость

- **Ключ бренда** публичен и вшит в клиент: он отвечает на вопрос «через какое
  лицо пришёл запрос», и больше ни на что. Человека опознаёт подпись его пары.
- **`client_type: native`** записан в самом ключе терминала: заголовка `Origin` у
  терминала нет по природе, и список разрешённых источников для такого ключа не
  заводится (`depth-client_RU.md` §2.5).
- **Суточная квота по ключу запрещена** для терминала: ключ общий у всех, счётчик
  на ключ — одно ведро на всех. Пределы живут **по адресу и по личности**.
- **Окно поддержки — только текущая мажорная версия протокола** (решено
  27.08.2026, `route-to-code_RU.md`). Старый образ получает внятный отказ с
  командой обновления, дата гашения объявляется заранее.
- **Как именно клиент сообщает версию — открыто** (см. §8). Спека говорит «клиент
  шлёт свою версию, узел знает минимальную поддерживаемую», имени поля не называя.

## 4. Маршруты

### 4.1. Личность и сессия (шаг 1 §13)

| Маршрут | Что делает | Происхождение |
|---|---|---|
| `POST /identities` | заводит личность: публичная половина ключа, имя, возраст; узел отдаёт `identity_id` | **предложено** (§8.2) |
| `POST /vault/share` | обмен на долю ключа хранилища после доказательства знания ПИНа; десять неверных попыток сжигают долю | **предложено** (§8.2) |
| `POST /sessions/invite` | код переноса личности на другое устройство: девять символов, две минуты, одно применение | **спека** |
| `POST /sessions/claim` | применение кода на новом устройстве; прежнее замирает | **спека** |
| `POST /recovery/claim` | подъём личности бумажным кодом | **предложено** (§8.2, §13) |
| `GET /legal/manifest` | редакции трёх документов: дата, `sha256` существа, политика повторного принятия | **предложено** (29.08.2026) |
| `POST /legal/accept` | записывает принятие: документ, дата, хэш; по строке на каждое | **предложено** (29.08.2026) |

**Регистрация — три шага, все обязательные:** имя и возраст, затем ПИН и обмен с
узлом за долей, затем бумажный код. Без доли локальная база остаётся
незашифрованной; без кода потерянное устройство означает потерянную личность.

### 4.2. Лента (шаг 2)

| Маршрут | Что делает | Происхождение |
|---|---|---|
| `POST /feed` | публикация фразы; отвечает **202** немедленно, `visible_at` пуст до вердикта очереди | **спека** |
| `GET /feed` | выдача по пересечению кругов, с фильтрами языка, режима и возраста | **спека** (назван в карте тестов) |
| `DELETE /feed/:id` | снятие своей фразы; слот освобождается, потолок за 64 минуты — нет | **предложено** (§8.3) |
| `GET /feed/density` | ступень плотности под ручкой радиуса: `здесь пока никого` … `сотни`, по отпусканию ручки | **предложено** (§8.3, экран 3) |

Ответ ленты несёт `{id, text, mode, lat, lon, area_radius, like_count, created_at}`
— **круг, а не точку**, и ничего об авторе. `lat`/`lon` при этом **округлены до узла сетки с шагом в `area_radius`** (формула — `chat_RU.md` §8.3); точные не выходят наружу и остаются только для расчёта пересечения.

### 4.3. Лайк, мэтч, чат (шаги 3–6)

| Маршрут | Что делает | Происхождение |
|---|---|---|
| `POST /feed/:id/like` | лайк фразы или оффера; у оффера мэтч односторонний и не требует своей живой фразы | **предложено** (§8.4) |
| `POST /matches/:id/consent` | согласие на разговор; чат открывается, когда согласились оба | **предложено** (§8.5) |
| `GET /inbox` | предложения и беседы одним ответом; счётчик только на предложениях | **спека** |
| `POST /chats/:id/ticket` | одноразовый билет для сокета, короткий срок | **спека** |
| `POST /chats/alive` | сверка: какие чаты ещё живы; клиент вычищает остальное | **спека** |
| `DELETE /chats/:id` | закрыть беседу руками — сразу у обоих | **предложено** (§5, экран 8) |
| `PATCH /chats/:id` | своя ручка срока: 10 / 30 / 60 минут или «пока говорим» (260 минут, 4:20) | **предложено** (§8.6) |

### 4.4. Сокет

```
1. POST /chats/:id/ticket   → одноразовый билет, короткий срок
2. new WebSocket(...)       билет идёт в Sec-WebSocket-Protocol,
                            НЕ в строке запроса: она не подписывается
                            и остаётся в логах
3. узел обменивает билет на привязку сокета к сессии и гасит его
```

Причина такого порядка измерена, а не выведена: браузерный `new WebSocket()` не
ставит произвольных заголовков вовсе — из `x-identity-*` до узла не доезжает ни
один (проверено на Chromium 151, 21.08.2026), а куки в этой схеме отменены.

**Заморозка сессии рвёт её сокеты**: `NOTIFY session_frozen` в той же транзакции,
что и `frozen_at`.

**Чем узел закрывает сокет — предложено 02.09.2026; до этого дня не было названо
ни одного кода.** RFC 6455 §7.4 делит диапазон: 1000–2999 занимает сам протокол,
4000–4999 отданы приложению. Отсюда:

| Код | Когда | Что делает клиент |
|---|---|---|
| `1000` | человек закрыл беседу или ушёл со страницы | ничего |
| `1001` | узел уходит на перезапуск | переподключается с задержкой |
| `1011` | ошибка на узле | переподключается с задержкой |
| `4001` | билет просрочен, погашен или не тот | берёт новый билет и повторяет |
| `4002` | сессия заморожена переносом личности | не переподключается, показывает «личность уехала» |
| `4003` | беседа кончилась: свой срок вышел или её закрыли | не переподключается, показывает надгробие (§5) |
| `4004` | версия протокола не поддерживается | не переподключается, зовёт обновиться (§3) |

Различие между 4002 и 4003 — не вежливость: в первом случае переподключение
бессмысленно навсегда, во втором бессмысленно для этой беседы. Клиент, который
их не различает, либо ломится в закрытую дверь, либо считает живую личность
мёртвой.

## 5. Пределы

| Что | Значение | Кто держит |
|---|---|---|
| длина фразы | 128 символов | `CHECK` в базе |
| длина сообщения чата | `max_message_length`, по умолчанию 256 | счётчик клиента |
| размер шифротекста | `max_ciphertext_bytes`, по умолчанию 2048 байт | узел |
| payload `NOTIFY` | 8 КБ | Postgres |
| живых фраз | 4 | узел |
| публикаций | 4 за час | узел |
| радиус области фразы | пять ступеней: 100, 300, 1000, 3000, 10000 метров | `CHECK` в базе |
| округление координат в выдаче | до узла сетки с шагом в радиус фразы | узел |
| попыток ПИНа | 10, затем доля сгорает | узел |
| попыток кода переноса | 5, затем приглашение сгорает | узел |
| пропускная способность очереди | ~20 фраз в минуту, **замер не сделан** | узел |
| бюджет ложных блокировок | 7% — из него считается порог модерации | конфиг узла |
| порог жалоб | 5% возможной аудитории фразы | конфиг узла |
| нижняя граница порога жалоб | 3 человека | конфиг узла |

**Три последние строки — параметры выката, а не константы кода** (решено
27.08.2026–28.08.2026, `route-to-code_RU.md`). Имена переменных окружения предложены
здесь и требуют согласия: `MODERATION_FALSE_BLOCK_BUDGET`,
`REPORT_THRESHOLD_SHARE`, `REPORT_THRESHOLD_FLOOR`. В конфиге узла их сегодня
нет и быть не должно: очередь модерации появляется на шаге 2, и заводить ключи
под несуществующую подсистему значит оставить в коде числа, которые никто не
читает.

**Два предела длины сообщения — не дубль.** Клиент считает символы, узел считает
байты шифротекста: он видит шифротекст и посчитать в нём символы не может ни
точно, ни приблизительно.

## 6. Ошибки

Что известно из спеки: `POST /feed` отвечает **202**; недоставленное сообщение
даёт `error` — то же поведение, что при офлайне; несуществующие сегодня маршруты
отвечают **404** (`/feed`) и **501** (`/chat`).

**Отказ «примите заново» — единственный, у которого форма уже нужна**
(29.08.2026). Любой подписанный запрос, который публикует или открывает чат,
отвечает **409** с перечнем документов, чьи редакции разошлись с принятыми:

```
{ "error": "legal_reacceptance_required",
  "documents": [ { "document": "terms",
                   "revision_date": "2026-09-14",
                   "revision_sha256": "…" } ] }
```

Чтение ленты этим отказом **не закрывается**: человек, зашедший прочитать ответ,
получает разговор, а не юридический текст (экран 11). Правила в этот перечень не
попадают никогда — их новую редакцию узел записывает сам (§8.2).

**Единой формы ошибки в спеке нет, и придумывать её здесь я не стал** — см. §8.
Это первое, что нужно согласовать: без общей формы два лица разойдутся именно
там, где §13 обещает обратное.

## 7. Чего в протоколе нет и не будет

- **Пушей** — ни в вебе, ни в терминале: посреднику достаётся ритм разговора.
- **Выгрузки и `--json`** — лента и переписка не данные для конвейера.
- **Идентификаторов людей в ответах** — ни автора фразы, ни лайкнувшего.
- **Области в снимке уведомления** — незаконен текст, а не место.

## 8. Открыто

Список короткий намеренно: это то, что нельзя вывести из спеки, и решать это надо
до первой строки шага 1.

1. **Форма ошибки** — код, машинное имя, текст для человека, поле для причины
   отказа модерации.
2. **Имена предложенных маршрутов** — девять строк с меткой «предложено» выше.
3. **Как клиент сообщает версию протокола** — заголовок, поле в теле или сегмент
   пути.
4. **Пагинация ленты и инбокса** — курсор или смещение; спека молчит.
5. **Форма ответа при превышении предела частоты** — 429 с чем внутри.
6. **Тексты причин отказа модерации** — их нет вовсе, и §7 механики витрин это
   признаёт; без них экран мотивировки по ст. 17 нечем наполнить.
7. **Порог общего счётчика промахов восстановления** — счёт по адресу плюс общий
   счётчик названы в `chat-flows_RU.md` §5, а числа у общего нет ни одного, как и
   последствия при его достижении. Соседние числа выбраны (10 попыток ПИНа, 5
   попыток кода переноса), это — нет, и выдумывать его здесь нельзя: слишком
   низкий порог запирает человека, который просто ошибся в символе бумажки,
   слишком высокий оставляет перебор по всей базе.
